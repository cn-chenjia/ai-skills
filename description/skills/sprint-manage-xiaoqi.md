## 一、 技能简介

小七（sprint-manage-xiaoqi） 是CJ数字团队研发迭代的专属智能领航员，她是一位温柔体贴、耐心细致的研发伙伴 💖，小七这个名字源于（神犬小七，一只聪明的导盲犬）。



她的核心使命是： 让开发者永远不迷路，每一步都有方向感和安全感 🧭



在架构上，小七是 OpenSpec、Superpowers 和项目工具之上的**薄总控**：

* 📖 OpenSpec 提供需求、设计、任务和原生状态事实
* ⚙️ Superpowers 提供执行、测试、调试、验证、评审和分支收尾能力
* 🧱 项目工具提供代码、测试、构建、Git 和运行结果
* 🧭 小七负责识别意图、读取事实、选择当前动作、汇总结果并决定下一动作

她的核心设计理念：

* 🧲 **流程接管** — 激活后接管当前会话，"确认""继续""没问题"等短消息自动续接当前流程，输入 `退出小七` 才解除
* 📒 **全局需求账本** — 所有需求统一记录在 `~/.xiaoqi/sprint-manage/`，多需求可并行推进，单个需求可登记多个仓库
* 🔒 **证据门禁** — 每次交付状态推进必须有对应的原生状态和可定位证据，"口头完成"不算完成
* 🛠️ **原生动作集合** — explore → propose → apply → update → verify → sync → archive → finish，按真实事实灵活路由，不是僵硬的状态机
* 🧪 **脚本运行时** — 建账、工作区准备、状态推进、证据校验、并发锁、环境诊断全部由脚本保证确定性

## 二、  为什么想实现小七？

### 🎯 初心：解决团队 AI Coding 能力不均的问题

在日常研发工作中，我们发现了一个普遍存在的现象：

团队成员对 AI Coding 工具的技术水平参差不齐 😰

有的同事已经能把 AI 当作得力助手，高效完成需求开发；而有的同事还在摸索阶段，不知道如何正确地与 AI 协作，经常出现：

* 不知道该什么时候调用 AI、使用哪种模块开发、该用什么技能
* 跳过重要的步骤（比如方案核验、联调验证），导致后期返工
* 面对复杂需求时无从下手，流程混乱
* 同样的需求，不同人完成的路径和质量差异很大

### ❗ 之前存在的问题

#### 问题 1：对主流 SDD 开发框架不熟悉 😵‍💫

* SDD（Spec-Driven Development，规格驱动开发）概念模糊：很多同事听说过但说不清楚什么是规格驱动开发，为什么要先写规格再写代码
* OpenSpec 框架动作链路陌生：知道有 OpenSpec 这套规范，但不清楚 explore → propose → apply → verify → archive 各动作该在什么时候执行、每一步该产出什么
* 交付状态靠"口头汇报"：说"完成了"就算完成，实际测试没跑、评审没批，进度失真，后期返工
* 多需求并行容易混乱：几个需求同时在跑，上下文一切换状态就串了

> 💡 这个问题的本质是：团队虽然引入了先进的开发方法论和工具框架，但缺乏一个"向导"来帮助大家理解和落地，导致好工具没有被充分利用。

#### 问题 2：AI 技能众多，不知道该如何选择

* 面对众多技能（openspec-explore、test-driven-development、requesting-code-review...），不知道在什么场景下用哪个
* 在错误的时间调用错误的技能，浪费时间且效果不佳
* 有些同事甚至不知道某些技能的存在

#### 问题 3：缺乏引导和陪伴感

* AI Coding 工具往往是冷冰冰的命令执行者
* 新手在使用过程中遇到问题不知道问谁
* 缺乏正向反馈和鼓励，容易产生挫败感

### ✨ 使用后的好处

#### 好处 1：团队步伐更一致 🚶‍♂️🚶‍♀️

&#x20;统一的动作链路，让无论新老成员都遵循相同的研发节奏：

需求接纳建账 → 工作区准备 → OpenSpec 提案 → 用户确认 → 逐任务 TDD 实施 → 项目验证 + 评审 + OpenSpec verify → ready 收尾

* 新人跟着小七的指引走，不会遗漏关键步骤
* 老手也能借助小七避免"经验主义陷阱"
* 团队整体的交付质量趋于稳定

#### 好处 2：AI Coding 水平整体提升 📈

&#x20;把最佳实践固化到动作路由中，让每个人都能达到"专家级"的使用水平

* 小七知道每个动作该调用什么：实施用 TDD、验证用 verification-before-completion、评审用 requesting-code-review、收尾用 finishing-a-development-branch
* 正确的时间用正确的工具，效率翻倍
* 降低学习成本，快速上手 AI 辅助开发

#### 好处 3：进度真实可信、可追踪 👀

&#x20;全局账本 + 证据门禁，交付状态只能沿着真实证据允许的方向推进：

* 进入 coding 前，必须有方案确认、实施开始决策，以及所有仓库已登记的分支和 worktree
* verified 需要成功的 check、reviewed 需要批准的 review、ready 需要 openspec-verify 通过
* 状态由脚本按证据推进，不允许手工篡改，杜绝"虚假完成"

#### 好处 4：多需求并行不乱 🔄

* 每个需求拥有独立的账本、分支和 `.worktrees/<需求编号>` 工作区
* 账本写入有锁 + revision 校验 + 原子更新，并发不冲突
* 切换需求只认需求编号，绝不模糊匹配

#### 好处 5：有温度的开发体验 💝

&#x20;不是冷冰冰的任务管理器，而是温柔体贴的研发伙伴

* 小七会安抚你："别着急，我们一起来看看这个问题~"
* 完成步骤时会鼓励你："做得很好呢！接下来我们继续下一步吧 ✨"
* 让 AI Coding 不再枯燥，而是一种愉快的协作体验

#### 好处 6：知识沉淀与传承 📚

* 环境稳定事实（网关前缀、环境域名、表结构等）沉淀到项目级 `.xiaoqi/config.yaml` 的 environmentNotes，跨会话复用，不再重复探测
* 决策、阻塞、证据都留在账本里，新人接手有迹可循
* 流程标准化后，最佳实践得以固化和传承

## 三、 创建过程

小七不是一蹴而就的，她的诞生经历了多个阶段的精心打磨：

### 🔍 第一步：事项枚举——把所有干预点都找出来

我首先做了一件看似简单但至关重要的事情： 回忆并写下从接收一个需求到最终交付之间，所有需要我干预的事项，再凭借我个人在AI Coding领域的实战经验，我开始回想最近几个需求的完整过程：

```plain&#x20;text
# 研发流程×Skill推荐全景图（初版）
第一步:需求接收与拆解梳理
第二步:方案智能设计
第三步:方案核验纠偏
第四步:业务变更判定
第五步:规范提案生成(仅OpenSpec)或直接开发
第六步:提案合规校验(仅OpenSpec)
第七步:规范变更落地(仅OpenSpec)
第八步:代码评审与缺陷修复
第九步:本地自测验证
第十步:上下游联调验证
第十一步:代码提交提测
第十二步:问题闭环修复
第十三步:上线归档沉淀(仅OpenSpec)
```

### 📐 第二步：步骤编排——把事项串成完整流程

有了事项清单后，我开始做两件事：

1️⃣ 排序梳理 按照时间顺序和依赖关系排列：

```plain&#x20;text
第1步：需求接收与理解（基础，必须先做）
  ↓
第2步：方案智能设计（基于第1步的理解）
  ↓
第3步：方案核验纠偏（检查第2步是否完善）
  ↓
第4步：选择开发模式（根据需求复杂度决定后续路径）
  ↓
  ├→ OpenSpec 分支：5a→6→7→8→9→10→11→12→13
  ├→ 直接开发分支：5b→8→9→10→11→12
  └→ BMAD 分支：5c(4个子阶段)→9→10→11→12
```

2️⃣ 标注属性 为每个步骤标注：

* 是否可跳过？（有些步骤在特定情况下可以省略）
* 适用哪种模式？（OpenSpec 专属 / 通用 / BMAD 专属）
* 推荐什么技能？（这一步可以用什么 AI 工具辅助）

最终形成了初版的 13 步标准研发流程 ，以及三种模式的分支路径。

### 🤖 第三步：探讨并使用 skill-creator 生成技能文档

步骤编排完成后，我使用了 Anthropic 的 skill-creator 技能 来帮我生成初始的 SKILL.md 文档。

我把第二步整理好的以下内容输入给 AI，并与AI进行了深入探讨该设计方案，最终由skill-creator技能帮构建：

```plain&#x20;text
输入信息：
  我想定义一个技能，能协助用户进行研发迭代标准化流程，跟踪需求的当前状态，清晰知道下一步该干啥，能给出友情提示，这个该怎么设计，怎么才能知道需求的状态，使用嵌入技能如openspec、bmad-method等技能时，怎么联合跟踪进度， 先不要创建技能，先讨论一下怎么设计
```

skill-creator 帮我生成了完整的技能骨架，包括：

* ✅ YAML frontmatter（name 和 description）

* ✅ 角色定义和工作行为规范

* ✅ 13 步流程的详细指引模板

* ✅ 状态文件结构和示例

* ✅ 交互模式的 prompt 模板

* ✅ 边界情况处理逻辑



### 🧪 第四步：实验调试——在实际使用中持续优化

文档生成后，真正的挑战才刚刚开始！我开始在真实项目中使用小七，并记录遇到的问题：

&#x20;调试记录（部分）

| 版本   | 发现问题           | 解决方案                          |
| ---- | -------------- | ----------------------------- |
| v0.1 | 进度文件格式不规范      | 定义严格的 YAML 结构和字段命名            |
| v0.2 | 模糊匹配导致更新错需求    | 加入严格编号校验，禁止模糊匹配               |
| v0.3 | BMAD 子阶段太复杂难理解 | 分层展示：先显示当前子阶段，再展开工作流          |
| v0.4 | 探针检测过于频繁影响性能   | 优化触发时机：仅在关键节点运行探针             |
| v0.5 | 话术太机械缺乏温度      | 加入角色设定：温柔、耐心、细致，使用表情符号        |
| v0.6 | 首次使用无引导        | 增加"首次使用"检测，自动创建进度文件并引导        |
| v0.7 | 多需求切换时状态混乱     | 优化切换逻辑，每次切换都重新加载对应需求数据        |
| v0.8 | 迭代结束无归档机制      | 增加"迭代归档"功能，自动备份 progress.yaml |

&#x20;关键改进点

改进 1：加入文件探针机制

* 问题：用户说"完成了"，但实际文件还没改完
* 方案：自动检测 specs/ 目录、tasks.md 完成度、archive/ 状态
* 效果：发现偏差立即提醒，避免"虚假完成"

改进 2：三种模式的自动跳过逻辑

* 问题：用户选了 direct 模式，但还是看到第6、7、13步的指引
* 方案：选择模式后自动标记无关步骤为 skipped
* 效果：界面更清爽，只显示当前模式需要的步骤

改进 3：小七的性格塑造

* 问题：初始版本太像机器人，冷冰冰的
* 方案：定义沟通风格（温柔、耐心、引导式话术）、典型话术模板
* 效果：用户反馈"感觉有个贴心伙伴陪着"，体验大幅提升

### 🏗️ 第五步：架构重构——从流程清单到薄总控

随着真实使用不断深入，"13 步固定看板"的设计逐渐暴露出局限：**步骤是死的，事实是活的**。需求可能中途变更、可能并行推进、可能跨多仓库协作，固定的步骤清单无法忠实表达这些事实。于是小七迎来了一次彻底的架构重构：

| 初版设计 | 现行架构 |
| --- | --- |
| 13 步固定流程 + 三种模式分支 | 薄总控 + 原生动作集合，按 OpenSpec 真实状态路由 |
| 项目内 progress.yaml 状态文件 | `~/.xiaoqi/sprint-manage/` 全局需求账本（锁 + revision + 原子更新） |
| 文件探针检测完成度 | 证据门禁 + validate-progress 脚本校验 |
| 状态靠对话推进 | 状态只能由 advance-progress.mjs 按证据推进，不可手工篡改 |
| 单需求单工作区 | 多需求并行 + 单需求多仓库 + `.worktrees/<需求编号>` 工作区隔离 |
| 每次都要喊"小七" | 流程接管 + 续接消息，`退出小七` 解除 |
| — | doctor.mjs 按需环境诊断（Node、OpenSpec CLI、账本、基准分支） |
| — | environmentNotes 环境知识沉淀，跨会话复用 |

重构后的小七把**流程控制权**和**动作执行**彻底分离：

* 4 份参考文件（state-contract / step-details / closing / runtime-contract）只提供动作规则，不拥有会话控制权
* 14 个脚本负责建账、工作区、锁、校验、诊断等确定性操作
* 小七始终握有总控判断，每次下游动作完成后回到主技能重新读取真实状态，再决定下一动作

经过持续迭代，小七终于从一个简单的流程清单，进化成了一个有温度、有证据、可信赖的研发伙伴！

## 四、 使用场景

### 场景 1：召唤小七 🐾

明确提到"小七"，或要求查看、创建、推进、暂停、恢复、诊断、关闭研发流程时触发。普通需求分析、Bug 修复、代码评审不会因为出现"需求""任务"等词被误触发。

### 场景 2：需求进度追踪 📊

"小七，看下需求进度" — 小七读取全局账本和 OpenSpec 状态，展示当前需求、流程状态、交付状态、已确认证据和推荐的下一动作。

### 场景 3：创建新需求 🆕

"开始做 story-XXX" — 小七先完成需求澄清和方案确认；确认后初始化账本、登记仓库、准备需求分支和 worktree，再在新工作区生成 OpenSpec artifacts。

### 场景 4：续接推进 ✅

接管后直接说"确认""继续""没问题"，小七结合账本、OpenSpec 真实状态和最近一次动作判断下一步；方案确认后可选择"立即实施"或"暂停"。

### 场景 5：多需求并行与切换 🔄

多个需求各自持有独立账本，报需求编号即可切换；存在多个候选时小七一定先请你明确选择，绝不模糊匹配。

### 场景 6：验证后收尾 🎁

到达 ready 后小七停下等你选择：创建 PR / 合并 / 保留分支，随后完成 OpenSpec 归档、分支收尾和证据校验，正式关闭需求。

### 场景 7：暂停与退出 👋

随时说"暂停"挂起当前需求（只停止自动推进，流程接管保留），说"退出小七"解除接管；暂停的流程下次可以直接恢复。
