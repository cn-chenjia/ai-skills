# sprint-manage-xiaoqi

> 小七是 CJ 数字团队的研发迭代协调助手。她会读取需求的真实状态，安排下一步动作，并用可验证的证据推动需求从方案确认走向交付完成。

## 一、小七解决什么问题

研发需求通常分散在规格、代码、测试、分支和沟通记录中。小七把这些信息连接起来，让开发者随时知道：

- 当前在处理哪个需求。
- 需求处于什么状态。
- 下一步应该做什么。
- 哪些事项正在阻塞。
- “已经完成”是否有真实证据。

小七不会再造一套研发流程，而是在现有工具之上做协调：

| 角色 | 负责内容 |
| --- | --- |
| 小七 | 识别意图、读取状态、安排动作、记录决策与阻塞、索引交付证据 |
| OpenSpec | 保存需求、方案、设计、规格、任务，并负责规格校验、同步和归档 |
| Superpowers | 提供测试驱动开发、调试、验证、评审和分支收尾方法 |
| 项目工具 | 执行测试、构建、静态检查、Git、CI 等实际操作 |

核心原则：

> 原生工具决定事实，小七账本只记录跨工具的决策、阻塞和证据索引。

## 二、什么时候使用小七

以下情况适合使用：

- 创建、推进、暂停、恢复或关闭一个研发需求。
- 查看需求或迭代进度。
- 查询当前需求下一步该做什么。
- 诊断需求为什么卡住。
- 管理多个并行需求或多人协作。
- 项目已经存在 `sprint-manage/requirements/`，需要继续已有流程。

以下情况通常不需要使用：

- 只讨论一个想法，不需要跟踪研发状态。
- 普通代码实现、Bug 修复或代码评审。
- 只出现“需求”“任务”“修复”等词，但没有流程管理意图。

### 会话接管

用户明确提到“小七”或要求管理研发流程后，小七会接管当前会话。后续的“确认”“执行”“继续”“好”等简短回复，都会沿用当前需求上下文，不需要重复输入“小七”。

输入 `退出小七` 后，才会解除会话接管。

小七也可以处理暂停、切换需求或“先只看计划”等请求，但这些请求仍由小七记录和协调。

## 三、快速开始

### 1. 准备条件

使用前应确认：

- 项目已经使用 Git。
- OpenSpec CLI 和对应技能可用。
- Superpowers 技能可用。
- `sprint-manage-xiaoqi` 技能已经安装。

首次接入项目时，安装宿主会话规则：

```bash
# Codex
node "<小七技能安装目录>/scripts/install-host-rules.mjs" "<项目根目录>" codex

# Trae
node "<小七技能安装目录>/scripts/install-host-rules.mjs" "<项目根目录>" trae
```

`<小七技能安装目录>` 指已经安装的 `sprint-manage-xiaoqi` 技能目录，不是业务项目中的同名目录。

常见位置：

```text
# 直接使用本仓库
<本仓库>/skills/sprint-manage-xiaoqi

# 安装为个人技能
~/.agents/skills/sprint-manage-xiaoqi
<Codex 技能目录>/sprint-manage-xiaoqi
```

如果不确定实际位置，可以在已安装技能列表中找到 `sprint-manage-xiaoqi`，使用其
`SKILL.md` 所在目录。

安装器只维护自己负责的规则区块，不会覆盖已有规则。Codex 规则写入项目的 `AGENTS.md`；Trae 规则写入用户级全局规则。

可以运行只读体检确认环境：

```bash
node "<小七技能安装目录>/scripts/doctor.mjs" "<项目根目录>"
```

体检不会安装依赖、创建需求或修改项目。

如果 OpenSpec 或 Superpowers 缺失，体检会指出缺失项。先按提示完成安装，再重新运行体检；不要在依赖不完整时创建需求账本。

### 2. 发起需求

直接在对话中告诉小七目标，例如：

```text
小七，开始做 story-1001：为订单增加取消原因。
```

小七会：

1. 检查项目、OpenSpec、已有需求账本和工作区。
2. 在需要时调查问题并澄清需求。
3. 创建或完善需求方案。
4. 等待用户确认方案。

### 3. 确认并执行

用户回复：

```text
确认执行
```

小七随后会自动：

1. 创建需求账本。
2. 登记需求专属分支和工作区。
3. 按任务实施代码并运行检查。
4. 处理普通失败并重新验证。
5. 完成评审和规格一致性检查。
6. 推进到 `ready`。

除非遇到业务决策、高风险操作、权限问题或无法自动恢复的失败，小七不会在普通步骤之间反复要求确认。

### 4. 选择收尾方式

`ready` 表示需求已经通过验证，可以开始收尾，**不表示已经创建 PR、合并或关闭需求**。

到达 `ready` 后，用户需要选择：

- 创建 PR。
- 直接合并。
- 保留当前分支和工作区。

小七完成 OpenSpec 归档和分支收尾后，需求才会进入 `closed`。

## 四、完整工作流程

主流程如下：

```text
调查与澄清（按需）
  -> 创建方案
  -> 用户确认
  -> 创建账本和准备工作区
  -> 实施与测试
  -> 项目验证
  -> 代码评审
  -> OpenSpec 一致性检查
  -> ready
  -> 用户选择收尾方式
  -> OpenSpec 归档
  -> 分支收尾
  -> closed
```

小七使用以下原生动作进行导航：

| 动作 | 作用 |
| --- | --- |
| `explore` | 调查问题、澄清需求、比较方案，不承诺创建变更 |
| `propose` | 创建或完善 OpenSpec 需求资料 |
| `apply` | 按已确认任务实施代码 |
| `update` | 开发中需求、设计或任务发生变化时更新资料 |
| `verify` | 检查项目质量以及实现与规格是否一致 |
| `sync` | 按需提前同步主规格或共享规格 |
| `archive` | 归档 OpenSpec change 并更新主规格 |
| `finish` | 创建 PR、合并或保留分支等交付收尾 |

这些动作不是必须逐个执行的固定阶段。小七会根据 OpenSpec 状态、项目事实和用户意图选择下一步。

### 容易混淆的名称

| 名称 | 类型 | 含义 |
| --- | --- | --- |
| `verify` | 动作 | 执行项目质量和规格一致性检查 |
| `verified` | 交付状态 | 项目检查已经通过 |
| `ready` | 交付状态 | 验证、评审和规格检查均已通过，等待用户选择收尾方式 |
| `closed` | 流程状态 | 归档和分支收尾均已完成，需求正式结束 |

### 简单变更与复杂变更

范围清楚、风险较低、任务较少的变更，可以直接在用户确认后持续实施和验证。

以下情况通常按复杂变更处理：

- 跨模块或公共链路变更。
- 涉及数据库、公共接口或权限。
- 引入外部系统、新技术或迁移。
- 任务超过 5 项或存在明显依赖。
- 回归范围较大。
- 存在多个可独立并行的任务。

复杂变更会增加更细的计划、独立工作区、并行协作或子任务安排，但不会改变“用户先确认，模型持续执行到 `ready`”的主流程。

只有用户明确要求“先给我计划，不要执行”时，小七才会停在计划阶段。

## 五、每次启动时会检查什么

每次触发后，小七按以下顺序读取事实：

1. 定位项目根目录。
2. 扫描并校验 `sprint-manage/requirements/<id>.yaml`。
3. 运行 `openspec list --json` 获取真实 change 列表。
4. 精确识别需求编号和 `change_id`；存在多个候选时请用户确认。
5. 运行 `openspec status --change <id> --json` 获取目标 change 状态。
6. 新需求按需调查，并创建方案等待确认。
7. 用户确认后调用 `initialize-requirement.mjs` 创建账本。
8. 检查 Git、测试、评审、分支和工作区证据。
9. 实施前调用 `prepare-workspace.mjs` 登记专属工作区。
10. 执行动作，并回写决策、阻塞、证据和状态。

小七不会根据模糊编号、文件是否存在或口头说“完成了”来猜测状态。

## 六、需求账本与工作区

每个正在开发的需求拥有独立的：

```text
sprint-manage/requirements/<id>.yaml
OpenSpec change_id
base branch
Git branch
worktree
```

当前开发者正在处理的需求记录在：

```text
sprint-manage/local/session.yaml
```

该文件不提交 Git。

调查和方案阶段不要求提前创建工作区。准备实施时：

- 当前目录未被其他活跃需求占用，可以登记为该需求的专属工作区。
- 当前目录已被占用，则创建或复用 `.worktrees/<需求编号>`。
- 工作区准备失败时，不会推进需求状态。

### 单写入者规则

每个需求账本只允许 `协作.负责人` 写入。其他参与者通过代码、测试、PR 或任务结果交付，不直接并发修改同一个账本。

写入时必须经过账本锁、版本校验、原子更新和 `revision` 递增，避免多人互相覆盖。

### 多人并行开发

大型需求可以共用一个 OpenSpec change 和集成分支，但每个并行单元必须声明：

- `owner`
- `branch`
- `worktree`
- `write_scope`
- `depends_on`

只有写入范围不重叠、依赖已满足、公共契约稳定时才允许并行。共享文件、公共接口、数据库迁移和主配置必须指定单一负责人或明确落地顺序。

## 七、开发中发生变化时

需求、设计或任务在开发中变化时：

1. 暂停受影响的任务。
2. 保留原有 `change_id`。
3. 使用 OpenSpec `update` 更新相关资料。
4. 重新读取 OpenSpec 状态。
5. 调整受影响的执行安排。
6. 只重做受影响的任务和必要回归。

已经归档的需求再次变化时，保留原归档，并创建新的 OpenSpec change。

### Bug 修复

先判断现有规格是否正确：

| 情况 | 处理方式 |
| --- | --- |
| 规格正确，修复很小 | 直接修复，并先补复现测试 |
| 规格正确，影响较大 | 创建或使用 OpenSpec change |
| 规格错误，change 未归档 | 使用 `update` 修正规格 |
| 规格错误，change 已归档 | 创建新的 change |
| 无法判断 | 先 `explore`，不猜测业务事实 |

紧急降级时，需要记录原因、复现测试、回归结果、是否补建 change 和用户确认。

## 八、状态与证据

每个需求维护两类状态：

| 状态类型 | 可选值 | 说明 |
| --- | --- | --- |
| 流程状态 | `active`、`paused`、`blocked`、`closed` | 表示流程是否正在运行 |
| 交付状态 | `not-started`、`coding`、`verified`、`reviewed`、`ready`、`pr-open`、`merged`、`kept` | 表示交付推进到了哪里 |

交付状态只能按以下方向推进：

```text
not-started -> coding -> verified -> reviewed -> ready
ready -> pr-open | merged | kept
```

每一步都需要真实证据：

| 目标状态 | 所需证据 |
| --- | --- |
| `coding` | 成功的 `apply` 结果 |
| `verified` | 成功的项目检查结果 |
| `reviewed` | 结论为 `approved` 的评审结果 |
| `ready` | 通过的 OpenSpec 一致性检查 |
| `pr-open`、`merged`、`kept` | 对应的分支收尾结果 |

证据至少包含：

```yaml
kind:
command:
exit_code: 0
commit:
checked_at:
summary:
```

交付状态不能手工跳过。统一由 `advance-progress.mjs` 校验证据、前置状态、账本锁和版本后更新。

需求进入 `closed` 必须同时满足：

- OpenSpec archive 成功。
- Superpowers finish 成功。
- 最终交付状态为 `pr-open`、`merged` 或 `kept`。

## 九、失败、阻塞与恢复

测试、构建或普通规格检查第一次失败时，小七会先分析并尝试修复：

```text
执行失败
  -> 分析原因
  -> 自动修复
  -> 重试原动作
  -> 成功后继续
  -> 达到重试上限后 blocked
```

默认同一错误最多自动修复 3 次，不会无限重试。

以下情况会请求人工处理：

- 评审发现高风险问题。
- 需要权限或环境授权。
- 需要确认破坏性操作。
- 自动修复次数耗尽。
- 无法判断失败原因。
- 发现业务规则冲突。
- 工作区存在覆盖风险。
- 状态、分支、change 或账本无法可靠确认。

阻塞记录需要说明原因、开始时间、恢复条件和建议动作。恢复时，小七会重新检查账本、OpenSpec 和项目环境；条件满足后从建议动作继续，条件未满足时不会机械重试。

## 十、收尾与关闭

需求通过项目验证、代码评审和 OpenSpec 一致性检查后进入 `ready`。

接下来：

1. 等待用户选择创建 PR、合并或保留分支。
2. 按需同步规格。
3. 执行 OpenSpec archive。
4. 执行分支收尾。
5. 记录 `pr-open`、`merged` 或 `kept` 的真实结果。
6. 证据齐全后将流程状态更新为 `closed`。

关闭整个迭代时，小七会检查所有需求是否已经 `closed`。未完成的 change 不会被自动归档，也不会伪造收尾结果。

## 十一、Hook 与运行时接入

需求账本、状态推进、证据校验和手动导航不依赖 Hook。Hook 是可选增强能力，可用于：

- 记录会话启动和动作结果。
- 在动作前检查条件。
- 在失败后记录阻塞。
- 在关闭前检查最终证据。
- 提醒或拦截危险命令。

用户级运行时目录：

```text
~/.xiaoqi/runtime/
```

常见配置位置：

```text
# Codex
.codex/config.toml
.codex/hooks.json

# Trae
.trae/hooks.json
```

需要 Codex 自动接入时，显式运行：

```bash
node "<小七技能安装目录>/scripts/install-codex-integration.mjs"
```

所有由小七发起的命令都应经过受控执行器：限制允许的命令和写入范围，设置超时和输出上限，并要求破坏性操作显式确认。Hook 不能替代宿主提供的权限审批、沙箱和网络隔离。

## 十二、常见说法

| 用户说法 | 小七会做什么 |
| --- | --- |
| “小七，查看 story-1001 的进度” | 汇总流程状态、交付状态、证据、阻塞和下一步 |
| “小七，下一步做什么” | 根据真实状态推荐可执行动作 |
| “小七，开始做 story-1001” | 检查需求、change、分支和工作区后进入对应流程 |
| “小七，切换到 story-1002” | 更新本地会话并加载目标需求，不修改其他需求 |
| “小七，为什么卡住了” | 检查账本、OpenSpec、Git、权限和验证证据 |
| “小七，继续” | 从最近一次待确认或中断位置继续 |
| “小七，关闭迭代” | 检查所有需求是否关闭，并列出未完成事项 |
| “退出小七” | 解除当前会话的小七接管 |

常见触发词包括：

```text
需求进度
迭代进度
下一步该做什么
开始做需求
创建需求
继续需求
研发流程
需求跟踪
完成验证
归档需求
关闭迭代
诊断阻塞
恢复需求
小七
```
