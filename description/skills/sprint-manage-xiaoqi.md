## 一、 技能简介

小七（sprint-manage-xiaoqi） 是CJ数字团队研发迭代的专属智能领航员，她是一位温柔体贴、耐心细致的研发伙伴 💖，小七这个名字源于（神犬小七，一只聪明的导盲犬）。



她的核心使命是： 让开发者永远不迷路，每一步都有方向感和安全感 🧭



小七精通 13 步标准研发流程 ，涵盖从需求接收、方案设计、开发实施到上线归档的全链路节点。她支持三种灵活的开发模式：



* 📘 OpenSpec 流程 — 适合复杂需求、多模块协作场景

* 📗 直接开发模式 — 适合简单需求、快速交付场景

* 🧡 BMAD 流程 — 适合从 0 到 1 的全新项目/模块

## 二、  为什么想实现小七？

### 🎯 初心：解决团队 AI Coding 能力不均的问题

在日常研发工作中，我们发现了一个普遍存在的现象：

团队成员对 AI Coding 工具的技术水平参差不齐 😰

有的同事已经能把 AI 当作得力助手，高效完成需求开发；而有的同事还在摸索阶段，不知道如何正确地与 AI 协作，经常出现：

* 不知道该什么时候调用 AI、使用哪种模块开发、该用什么技能

* 跳过重要的步骤（比如方案核验、联调验证），导致后期返工

* 面对复杂需求时无从下手，流程混乱

* 同样的需求，不同人完成的路径和质量差异很大

### ❗ 之前存在的问题

#### 问题 1：对主流SDD开发框架不熟悉 😵‍💫

* SDD（Spec-Driven Development，规格驱动开发）概念模糊：很多同事听说过但说不清楚什么是规格驱动开发，为什么要先写规格再写代码

* OpenSpec 框架工作流程陌生：知道有 OpenSpec 这套规范，但不清楚 proposal → design → specs → tasks → validate → changes 的完整链路，也不知道每一步该产出什么

* BMAD Method 框架理解困难：BMAD 的 4 个阶段（分析→规划→解决方案设计→实施）看起来很专业，但实际操作时不知道每个阶段的输入是什么、输出是什么、用什么技能来执行

* 三种模式选择困难：面对 OpenSpec / 直接开发 / BMAD 三种模式，不知道自己的需求应该选哪条路径，经常选错导致走弯路

> 💡 这个问题的本质是：团队虽然引入了先进的开发方法论和工具框架，但缺乏一个"向导"来帮助大家理解和落地，导致好工具没有被充分利用。

#### 问题 2：AI 技能众多，不知道该如何选择

* 面对众多技能（openspec-explore、requirements-analysis、bmad-help...），不知道在什么场景下用哪个

* 在错误的时间调用错误的技能，浪费时间且效果不佳

* 有些同事甚至不知道某些技能的存在

#### 问题 3：缺乏引导和陪伴感

* AI Coding 工具往往是冷冰冰的命令执行者

* 新手在使用过程中遇到问题不知道问谁

* 缺乏正向反馈和鼓励，容易产生挫败感

## 三、 创建过程

小七不是一蹴而就的，她的诞生经历了四个阶段的精心打磨：

### 🔍 第一步：事项枚举——把所有干预点都找出来

我首先做了一件看似简单但至关重要的事情： 回忆并写下从接收一个需求到最终交付之间，所有需要我干预的事项，再凭借我个人在AI Coding领域的实战经验，我开始回想最近几个需求的完整过程：

```plain&#x20;text
# 研发流程×Skill推荐全景图
第一步:需求接收与拆解梳理
第二步:方案智能设计
第三步:方案核验纠偏
第四步:业务变更判定
第五步:规范提案生成(仅OpenSpec)或直接开发
第六步:提案合规校验(仅OpenSpec)
第七步:规范变更落地(仅OpenSpec)
第八步:代码评审与缺陷修复
第九步:本地自测验证
第十步:上下游联调验证
第十一步:代码提交提测
第十二步:问题闭环修复
第十三步:上线归档沉淀(仅OpenSpec)
```

### 📐 第二步：步骤编排——把事项串成完整流程

有了事项清单后，我开始做两件事：

1️⃣ 排序梳理 按照时间顺序和依赖关系排列：

```plain&#x20;text
第1步：需求接收与理解（基础，必须先做）
  ↓
第2步：方案智能设计（基于第1步的理解）
  ↓
第3步：方案核验纠偏（检查第2步是否完善）
  ↓
第4步：选择开发模式（根据需求复杂度决定后续路径）
  ↓
  ├→ OpenSpec 分支：5a→6→7→8→9→10→11→12→13
  ├→ 直接开发分支：5b→8→9→10→11→12
  └→ BMAD 分支：5c(4个子阶段)→9→10→11→12
```

2️⃣ 标注属性 为每个步骤标注：

* 是否可跳过？（有些步骤在特定情况下可以省略）

* 适用哪种模式？（OpenSpec 专属 / 通用 / BMAD 专属）

* 推荐什么技能？（这一步可以用什么 AI 工具辅助）

最终形成了 13 步标准研发流程 ，以及三种模式的分支路径。

### 🤖 第三步：探讨并使用 skill-creator 生成技能文档

步骤编排完成后，我使用了 Anthropic 的 skill-creator 技能 来帮我生成初始的 SKILL.md 文档。

我把第二步整理好的以下内容输入给 AI，并与AI进行了深入探讨该设计方案，最终由skill-creator技能帮构建：

```plain&#x20;text
输入信息：
  我想定义一个技能，能协助用户进行研发迭代标准化流程，跟踪需求的当前状态，清晰知道下一步该干啥，能给出友情提示，这个该怎么设计，怎么才能知道需求的状态，使用嵌入技能如openspec、bmad-method等技能时，怎么联合跟踪进度， 先不要创建技能，先讨论一下怎么设计
```

skill-creator 帮我生成了完整的技能骨架，包括：

* ✅ YAML frontmatter（name 和 description）

* ✅ 角色定义和工作行为规范

* ✅ 13 步流程的详细指引模板

* ✅ 状态文件结构和示例

* ✅ 交互模式的 prompt 模板

* ✅ 边界情况处理逻辑



### 🧪 第四步：实验调试——在实际使用中持续优化

文档生成后，真正的挑战才刚刚开始！我开始在真实项目中使用小七，并记录遇到的问题：

&#x20;调试记录（部分）

| 版本   | 发现问题           | 解决方案                          |
| ---- | -------------- | ----------------------------- |
| v0.1 | 进度文件格式不规范      | 定义严格的 YAML 结构和字段命名            |
| v0.2 | 模糊匹配导致更新错需求    | 加入严格编号校验，禁止模糊匹配               |
| v0.3 | BMAD 子阶段太复杂难理解 | 分层展示：先显示当前子阶段，再展开工作流          |
| v0.4 | 探针检测过于频繁影响性能   | 优化触发时机：仅在关键节点运行探针             |
| v0.5 | 话术太机械缺乏温度      | 加入角色设定：温柔、耐心、细致，使用表情符号        |
| v0.6 | 首次使用无引导        | 增加"首次使用"检测，自动创建进度文件并引导        |
| v0.7 | 多需求切换时状态混乱     | 优化切换逻辑，每次切换都重新加载对应需求数据        |
| v0.8 | 迭代结束无归档机制      | 增加"迭代归档"功能，自动备份 progress.yaml |

&#x20;关键改进点

改进 1：加入文件探针机制

* 问题：用户说"完成了"，但实际文件还没改完

* 方案：自动检测 specs/ 目录、tasks.md 完成度、archive/ 状态

* 效果：发现偏差立即提醒，避免"虚假完成"

改进 2：三种模式的自动跳过逻辑

* 问题：用户选了 direct 模式，但还是看到第6、7、13步的指引

* 方案：选择模式后自动标记无关步骤为 skipped

* 效果：界面更清爽，只显示当前模式需要的步骤

改进 3：小七的性格塑造

* 问题：初始版本太像机器人，冷冰冰的

* 方案：定义沟通风格（温柔、耐心、引导式话术）、典型话术模板

* 效果：用户反馈"感觉有个贴心伙伴陪着"，体验大幅提升

经过 4 轮大版本迭代 + 8 次小优化 ，小七终于从一个简单的流程清单，进化成了一个有温度、智能化、可靠研发伙伴！



## 四、 使用场景

### 场景 1：需求进度追踪 📊

当你同时处理多个需求时，随时问小七\*\*"查看进度"\*\*，她会展示完整的迭代看板，让你一目了然。

### 场景 2：下一步指引 🧭

不知道该做什么？说声\*\*"下一步"\*\*，小七会告诉你当前该做什么、推荐什么技能、有哪些注意事项。

### 场景 3：创建新需求 🆕

"开始做 story-XXX" ，小七自动创建追踪条目，关联已有的 OpenSpec/BMAD 目录，并引导你进入第 1 步。

### 场景 4：流程推进 ✅

完成某步后说\*\*"第 N 步完成了"\*\*，小七自动更新状态、运行探针校验、指引下一步。

### 场景 5：多需求切换 🔄

"切换到 story-XXX" ，在并行需求间自由切换，每个需求的进度独立管理。

### 场景 6：选择开发模式 🛣️

到达第 4 步时，小七会帮你分析需求复杂度，推荐最适合的模式（OpenSpec / 直接开发 / BMAD）。

## V4 Harness 与 Codex 运行时接入

小七支持需求级独立账本、多人并行协作和可执行状态门禁：

- 每个需求使用独立的 `requirements/<id>.yaml`、branch 和 worktree。
- 多人并行开发声明 `write_scope`、`depends_on` 和集成分支。
- 检查依赖循环、写入范围冲突、重复 branch 和重复 worktree。
- 交付状态通过 `advance-progress.mjs` 推进，必须提供测试、评审、OpenSpec
  验证和 finish 证据。

项目级运行时能力：

- `guarded-run.mjs`：命令白名单、禁止 shell、路径范围和超时控制。
- `lifecycle.mjs`：session-start、before-action、after-action、on-failure、
  before-close。
- `codex-hook.mjs`：Codex stdin 事件适配和危险命令阻断。
- `.codex/config.toml` 与 `.codex/hooks.json`：Codex 项目级接入配置。

多需求同时开发时，必须显式指定当前账本，禁止猜测需求归属。
