## 一、 技能简介

模块系统文档整理（business-scenario-documenter）是 CJ 数字团队的"代码翻译官" 📚，她能把一个陌生的系统模块，整理成一份业务人员看得懂、开发人员用得上的模块系统文档。

她的核心使命是： 让每一个模块都有清晰、可信、可传承的文档 🗺️

她把一份模块文档拆成三部分，并且有明确的优先级：

* 🎯 **模块定位** — 职责与边界、归属与上下游、核心价值、触发业务场景
* 🔌 **接口与数据流**（最优先） — 对外暴露（HTTP/Dubbo/MQ/定时任务/触发器）、数据流向、核心数据模型和状态机
* 🏗️ **内部架构与核心流程** — 分层结构、主流程时序图、失败/重试/补偿/降级/兜底分支、中间件依赖

她的核心设计理念：

* 🧲 **接口先行** — 先盘清"对外暴露什么、数据从哪来到哪去"，再谈内部实现，避免一上来就陷入代码细节
* 🤖 **状态机是重灾区** — 每条状态迁移必须对应真实业务动作和触发条件，不把接口中间状态、按钮名称当成业务状态
* 🔍 **证据优先** — 业务代码优先用 codegraph 沿调用链追踪，数据库优先用 mysql-mcp-server 只读确认，当前代码和数据库模型永远优先于历史文档
* ✅ **三层准确性评估** — 事实支撑层、条件分支层、实现对应层逐条核对，杜绝"一定会""所有场景都"这类没有依据的绝对表述
* 📝 **只输出结果** — 最终文档只写整理结果、代码定位和必要的待确认项，不输出取证过程

## 二、 为什么想实现她？

### 🎯 初心：让"祖传代码"不再是黑盒

在日常工作中，我们经常遇到这样的场景：要接手一个老模块、要给新同事讲一个系统、要给上下游团队对齐接口，结果发现：

* 没有文档，或者文档是三年前写的，和当前实现对不上 😵
* 只有业务描述，没有代码定位，出了问题不知道从哪查起
* 时序图画得很漂亮，但状态流转全是错的——把页面按钮、接口中间态当成了业务状态
* 文档里的"一定会""必然生成"，实际上只在部分条件下成立，误导排查方向

> 💡 这个问题的本质是：文档不是从当前代码和数据库"取证"出来的，而是凭记忆和想象写出来的。

### ✨ 使用后的好处

#### 好处 1：文档结构统一，人人能看懂 📐

严格按四章模板输出：模块定位 → 接口与数据流 → 内部架构与核心流程 → 参考文档。不管是接手、评审还是交接，翻开就知道去哪找什么。

#### 好处 2：接口与数据流盘点完整 🔌

页面、HTTP、Dubbo、MQ、定时任务、数据库触发器，所有对外入口一个不漏；核心入口展开写清入参、出参、错误码、限流、超时、重试策略，并附 Controller/Service/核心方法的代码定位。

#### 好处 3：状态机经得起推敲 🔄

每个业务对象单独一张 `stateDiagram-v2` 状态机，每条迁移都对照状态枚举、状态更新代码和数据库状态字段逐条核实，告别"想当然"的状态图。

#### 好处 4：准确且有据可查 🔍

文档生成后强制执行一轮独立的准确性评估，按"事实支撑 → 条件分支 → 实现对应"三层检查，高风险断言（绝对表述、接口地址、状态迁移、表关系、上下游调用）逐条回溯代码和数据库；找不到支撑的直接改为"待确认"或删除。

#### 好处 5：一键导入飞书，图形不丢 💝

输出的 Markdown 和 Mermaid 全部兼容飞书文档导入；导入时逐段识别 Mermaid 代码块，自动放入飞书的"放大文本绘图组件"，流程图、时序图、状态图、ER 图都能正常展示，而不是变成一坨源码文本。

## 三、 创建过程

### 📐 第一步：定结构——三部分文档骨架

先确定文档的三部分划分和优先级：模块定位、接口与数据流（最优先）、内部架构与核心流程。特别是把"接口与数据流"提到最前面，强制先盘对外暴露、数据流向、数据模型和状态机，再进入内部实现。

### 🧩 第二步：写模板——scenario-template.md

把骨架落成可直接填写的 Markdown 模板，内置全部 Mermaid 示例：

* 触发业务场景、数据流向 → `flowchart`
* 主流程 → 最简 `sequenceDiagram`
* 状态机 → 每个业务对象一张 `stateDiagram-v2`
* 数据模型 → `erDiagram`（表框只保留表达关系所需的主键/外键/关联字段）

模板里明确"不使用 HTML、内嵌 SVG、图片 data URI"，保证飞书导入兼容。

### ✅ 第三步：定清单——evidence-checklist.md

设计内部核对清单，覆盖 8 个维度：模块范围、触发业务场景、状态和数据、接口与核心流程、工具使用、文档准确性评估、输出质量、飞书云盘导入。清单只用于整理过程自检，不出现在最终交付文档里。

### 🛠️ 第四步：定工具链——codegraph + mysql-mcp-server

* 业务代码：优先 codegraph 按符号查询、沿调用链追踪；索引不可用时才降级到文件搜索
* 数据库：优先 mysql-mcp-server 只读确认表结构、状态字段和单据关联；不可用时才读建表脚本和实体类
* 历史文档：PRD、接口文档、会议纪要只用于补充业务术语和场景名称，当前代码和数据库永远优先

### 🤖 第五步：加保险——准确性评估与飞书导入门禁

* 强制"生成 → 评估 → 修复 → 再检查"闭环，三层检查确保文档与当前实现一致
* 飞书导入设置双重门禁：用户没给目录位置不导入，给了位置没明确确认也不导入；导入后还要检查章节和绘图组件是否齐全

## 四、 使用场景

### 场景 1：接手陌生模块 🗺️

"帮我把订单模块整理成文档" — 从模块定位到主流程时序图，一份完整文档带你快速理解模块全貌。

### 场景 2：接口与上下游对齐 🔌

"盘一下这个模块对外暴露了哪些接口和消息" — 完整列举 HTTP/Dubbo/MQ/定时任务/触发器入口，附调用方、入参出参和代码定位，对齐会上一目了然。

### 场景 3：状态流转梳理 🔄

"这个单据的状态机是怎么流转的" — 逐条核对状态枚举、状态更新代码和数据库状态字段，输出可信的状态机图和状态说明表。

### 场景 4：异常分支排查 🚨

"失败、重试、补偿、降级、兜底都有哪些逻辑" — 逐条写清触发条件、处理方式和结果，排查线上问题时直接对照。

### 场景 5：文档沉淀到飞书 💝

文档生成并通过准确性评估后，提供飞书云盘目录位置并确认，即可导入飞书，Mermaid 图形自动放入"放大文本绘图组件"正常展示。
