# 13 步研发流程详细指引

## 第1步：需求接收与理解

### 目的
精准理解业务意图，提炼需求核心目标、改动范围与关键约束。

### 完成条件
- 明确了需求的核心目标（要解决什么问题）
- 明确了改动范围（涉及哪些模块/接口/数据表）
- 明确了关键约束（性能要求、兼容性、时间节点等）

### 智能判断逻辑
根据用户提供的需求信息完整度，自动选择处理方式：

| 需求信息完整度 | 判断依据 | 处理方式 |
|----------------|----------|----------|
| 明确 | 用户提供了核心目标、改动范围、关键约束中的至少2项 | 直接执行第1步，自动完成并推进 |
| 模糊 | 用户仅提供需求标题或简短描述，缺少关键信息 | 输出引导，提示补充缺失信息 |

### 探针逻辑
- 检查用户是否已在对话中明确表述了核心目标、改动范围与关键约束
- 如果信息完整，自动标记第1步为 completed 并推进到第2步
- 如果信息不完整，保持第1步为 in_progress，输出引导提示

### 推荐技能
- **requirements-analysis**：从模糊需求中提取核心目标、范围与约束（需求模糊时推荐）

### 指引输出

**需求明确时，直接执行并自动完成：**
```
✅ 第1步「需求接收与理解」已完成！

💡 已识别需求信息：
   - 🎯 核心目标：xxx
   - 📐 改动范围：xxx
   - 🔒 关键约束：xxx

📌 下一步：第2步 方案智能设计（可跳过）
🎯 推荐技能：openspec-explore
```

**需求模糊时，输出引导：**
```
📊 需求状态：进行中 | 📌 当前：第1步 需求接收与理解

💡 收到需求，但还需要补充以下信息才能继续：
   - 🎯 核心目标：这个需求要解决什么问题？
   - 📐 改动范围：涉及哪些模块、接口、数据表？
   - 🔒 关键约束：有什么限制条件、兼容性要求、依赖关系？

🎯 推荐技能：requirements-analysis → 从模糊需求中提取核心目标、范围与约束

你可以告诉我：
   - 📖 "查看进度" — 查看当前迭代看板
   - ✅ "第1步完成了" — 需求信息已明确，推进到下一步
   - 🆕 "创建需求 story-XXX" — 追踪新需求
   - 🔄 "切换到 story-XXX" — 切换查看不同需求
```

## 第2步：方案智能设计

### 目的
基于梳理后的核心需求，输出标准化设计方案。

### 完成条件
- 对话中明确设计方案
- 方案包含：技术选型、接口设计、数据模型、流程图等

### 可跳过
是。适用于开发者对需求非常熟悉、改动范围小的情况。

### 探针逻辑
- 检查用户是否已在对话中明确设计方案

### 推荐技能
- **openspec-explore**：探索模块实现，辅助方案设计

### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第2步 方案智能设计

💡 第2步需要你输出设计方案，包含：
   - 🏗️ 技术选型：用什么技术方案实现？
   - 🔌 接口设计：新增或修改哪些接口？
   - 💾 数据模型：涉及哪些表结构变更？
   - 📊 流程图：核心业务流程是怎样的？

🎯 推荐技能：openspec-explore → 探索模块实现，辅助方案设计

⏭ 这一步可以跳过（如果你对需求很熟悉）

你可以告诉我：
   - 📖 "查看进度" — 查看当前迭代看板
   - ➡️ "下一步" — 获取下一步指引
   - ✅ "第2步完成了" — 推进到下一步
   - ⏭ "跳过第2步" — 跳过当前步骤
   - 🆕 "创建需求 story-XXX" — 追踪新需求
   - 🔄 "切换到 story-XXX" — 切换查看不同需求
```

### 跳过提醒
```
⏭ 第2步「方案智能设计」已标记为跳过
⏭ 第3步「方案核验纠偏」自动跳过（无方案则无需核验）

💡 提醒：跳过方案设计可能导致后续实现偏离预期
   如果后续发现需要方案文档，可以随时回退补上

📌 当前步骤：第4步 选择开发模式
```

## 第3步：方案核验纠偏

### 目的
对设计方案进行核验，确保没有遗漏和偏差。

### 完成条件
- 方案已经过核验，确认无遗漏和偏差

### 可跳过
第2步跳过时自动跳过。第2步完成时可选跳过，但建议至少做一次快速核验。

### 探针逻辑
- 检查用户是否已在对话中确认方案无遗漏

### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第3步 方案核验纠偏

💡 第3步需要对设计方案进行核验：
   - ✅ 方案是否覆盖了所有需求点？
   - ✅ 是否有遗漏的边界场景？
   - ✅ 技术方案是否与现有架构兼容？

⏭ 这一步可以跳过，但建议至少做一次快速核验

你可以告诉我：
   - 📖 "查看进度" — 查看当前迭代看板
   - ➡️ "下一步" — 获取下一步指引
   - ✅ "第3步完成了" — 推进到下一步
   - ⏭ "跳过第3步" — 跳过当前步骤
   - 🆕 "创建需求 story-XXX" — 追踪新需求
   - 🔄 "切换到 story-XXX" — 切换查看不同需求
```

## 第4步：选择开发模式

### 目的
根据需求复杂度和时间约束，选择合适的开发流程。

### 完成条件
- 用户明确选择了开发模式（openspec、direct 或 bmad）

### 可跳过
否。这是流程分支的关键决策点。

### 探针逻辑
- 检查 progress.yaml 中是否有选择结果字段

### 模式选择指引

| 模式 | 适用场景 | 流程特点 |
|------|----------|----------|
| OpenSpec | 需求复杂、多模块、需规范化追踪 | 13步完整流程，含提案生成、合规校验、变更落地 |
| 直接开发 | 需求简单、改动小、时间紧迫 | 跳过6、7、13步，快速开发 |
| BMAD | 从0到1的新项目/新模块，需完整规划 | 4子阶段推进（分析→规划→方案设计→实施），跳过6、7步 |

### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第4步 选择开发模式

💡 请选择开发流程：
   - 📘 OpenSpec 流程：适合需求复杂、多模块、需规范化追踪的场景
   - 📗 直接开发：适合需求简单、改动小、时间紧迫的场景
   - 🧡 BMAD 流程：适合从0到1的新项目/新模块，需要完整的产品规划与架构设计

请告诉我你的选择："选 openspec"、"选直接开发" 或 "选 bmad"
```

## 第5a步：规范提案生成（OpenSpec）

### 目的
生成 OpenSpec 变更提案，包含 proposal/design/specs/tasks。

### 完成条件
- 变更目录下 specs/ 目录有 spec.md 文件
- proposal.md、design.md、tasks.md 已生成

### 可跳过
否。

### 探针逻辑
- 检查变更目录下 specs/ 目录是否有 spec.md 文件

### 推荐技能
- **openspec-propose**：创建 OpenSpec 变更提案（自动执行）

### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第5步 规范提案生成（自动执行）

💡 第4步选择了 OpenSpec 流程，正在自动调用 openspec-propose 技能生成提案...

🎯 执行技能：openspec-propose → 创建 OpenSpec 变更提案

⚠️ 注意：变更目录命名必须使用中文
   格式：禅道需求/任务/BUG-编号-需求名称
   示例：story-65724-内场工单点检工单改造

```

## 第5c步：BMAD流程实施

### 目的
通过 BMAD Method 的4阶段工作流，完成从分析、规划、方案设计到实施的全流程。

### 完成条件
- 4个子阶段全部完成（阶段1可选跳过）
- 阶段4（实施）中所有 story 已开发并通过代码评审

### 可跳过
否。但内部的阶段1（分析）可以跳过。

### 探针逻辑
- 阶段1：`_bmad-output/` 下有 `brainstorming-report.md` 或 `product-brief.md`
- 阶段2：`_bmad-output/planning-artifacts/` 下有 `PRD.md`
- 阶段3：`_bmad-output/planning-artifacts/` 下有 `architecture.md` 且 epics 目录有文件
- 阶段4：`_bmad-output/implementation-artifacts/` 下有 `sprint-status.yaml`

### 推荐技能
- **bmad-help**：BMAD 智能向导，检测项目状态并推荐下一步

### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第5步 BMAD流程实施

💡 第4步选择了 BMAD 流程，将通过4个子阶段完成从规划到实现的全流程：

   阶段1 - 分析（可选）：头脑风暴、研究、产品简报
   阶段2 - 规划：创建 PRD、UX 设计
   阶段3 - 解决方案设计：架构设计、史诗与故事拆分、实施就绪检查
   阶段4 - 实施：冲刺规划、故事开发、代码评审

🎯 推荐技能：bmad-help → BMAD 智能向导，检测项目状态并推荐下一步

⚠️ BMAD 工作流建议：
   - 每个工作流使用新对话，避免上下文限制
   - 产出目录：_bmad-output/
   - 每个子阶段完成后告诉我"阶段N完成了"
```

### 子阶段1：分析（可选）

#### 目的
在正式规划前，验证问题空间与关键假设。

#### 完成条件
- 完成头脑风暴或研究或产品简报（至少一项）
- 或用户选择跳过此阶段

#### 可跳过
是。如果需求目标已经非常明确，可以直接跳到阶段2。

#### 推荐技能
- **bmad-brainstorming**：引导式构思
- **bmad-domain-research** / **bmad-market-research** / **bmad-technical-research**：验证领域、市场与技术假设
- **bmad-create-product-brief**：沉淀产品方向与战略愿景
- **bmad-agent-analyst**：分析师智能体，引导头脑风暴与研究

#### 产出
- `_bmad-output/brainstorming-report.md`
- 研究发现文档
- `_bmad-output/product-brief.md`

#### 指引输出
```

### 子阶段3：解决方案设计

#### 目的
定义"如何实现"并拆分可交付工作单元。

#### 完成条件
- architecture.md 已生成
- epics 和 stories 已拆分
- 实施就绪检查通过（PASS 或 CONCERNS 可接受）

#### 可跳过
否。

#### 推荐技能
- **bmad-create-architecture**：创建架构文档，含 ADR
- **bmad-create-epics-and-stories**：将 PRD 拆分为可实施的 epics/stories
- **bmad-check-implementation-readiness**：实施前 gate 检查
- **bmad-agent-architect**：架构师智能体，引导架构设计与就绪检查

#### 产出
- `_bmad-output/planning-artifacts/architecture.md`
- epics 文件与 story 条目
- 实施就绪检查结论（PASS / CONCERNS / FAIL）

#### 指引输出

   📋 epics/ — 史诗与故事文件
   ✅ 实施就绪检查：PASS

#### 风险提醒
- 跳过实施就绪检查时：提醒可能存在规划与实现不一致的风险
- 实施就绪检查结果为 FAIL 时：必须修复问题后才能进入阶段4

### 子阶段4：实施

#### 目的
按 story 节奏持续交付与校验。

#### 完成条件
- 所有 story 已开发完成
- 代码评审通过
- sprint-status.yaml 中所有 story 状态为完成

#### 可跳过
否。

#### 推荐技能
- **bmad-sprint-planning**：初始化冲刺跟踪
- **bmad-create-story**：准备下一个可实施 story
- **bmad-dev-story**：按规范实现 story
- **bmad-code-review**：验证实现质量
- **bmad-agent-dev**：开发者智能体，引导冲刺规划与故事开发

#### 产出
- `_bmad-output/implementation-artifacts/sprint-status.yaml`
- story 文件
- 可运行代码与测试
- 代码审查结果

#### 指引输出
```
📊 需求状态：进行中 | 📌 当前：第5步 BMAD流程实施 → 阶段4 实施

💡 阶段4按 story 节奏持续交付与校验：
   - 🏃 冲刺规划（bmad-sprint-planning）— 初始化迭代追踪
