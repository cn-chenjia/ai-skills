# 模块深度核对清单

本清单用于整理过程中的内部检查。最终文档只输出业务结果、代码定位和必要的待确认项，不输出本清单或完整论证过程。

## 1. 模块范围

- 已确认模块职责、边界（不做什么）和核心业务对象。
- 已确认所属系统/子系统和核心价值类型（计算/存储/消息转发/权限/数据同步/对外 API 网关）。
- 已识别主要入口：页面、HTTP、Dubbo、MQ、定时任务、数据库触发器和外部回调。
- 已识别上游、下游系统和相互交换的内容。
- 已识别模块主状态和主要操作。

## 2. 触发业务场景

- 每个场景都有明确的触发来源、本模块动作和结果。
- 场景区分正常流程和典型异常场景。
- 场景之间没有重复描述，场景名称可以被业务人员理解。

## 3. 状态和数据

- 状态来自状态枚举、状态更新代码、状态校验或前端状态展示。
- 每个业务对象单独绘制状态机，每条迁移都对应真实操作或真实条件。
- 数据关系图只包含模块实际读写或关联的表。
- 数据关系图覆盖来源单据、状态关联、组织/账套、设备/人员、幂等和审计相关表的关系。
- 表框关键字段保留主键、外键、状态字段和关联字段。

## 4. 接口与核心流程

每个对外入口和主流程都需要检查：

- 入口类型、名称/地址、调用方或触发方式。
- 入参、出参、错误码、限流、超时、重试策略。
- Controller/Handler、Service 和核心方法的代码定位。
- 主流程时序图包含真实参与方、调用方向、数据库操作和上下游依赖。
- 失败、重试、补偿、降级、兜底分支的触发条件、处理方式和结果。
- 中间件依赖（Redis、MySQL、RocketMQ、ES 等）和其他服务接口依赖的用途和失败处理。

## 5. 工具使用

- 业务代码优先使用 `codegraph`；不可用时才使用文件搜索和读取。
- 数据库优先使用 `mysql-mcp-server`；不可用时才使用建表脚本、实体或 ERD。
- 所有数据库操作保持只读。
- 代码定位至少保留文件、类/方法；能定位行号时补充行号。

## 6. 文档准确性评估

生成文档后先定位高风险断言，再逐条核对：

### 事实是否有代码或数据库支撑

- 接口、方法、状态、数据表、表关系和上下游调用是否能在当前实现中找到。
- 找不到直接支撑的内容改为“待确认”或删除。

### 是否把条件分支写成必然

- 检查权限、状态、配置、组织/账套、数据存在性和外部调用结果。
- 将“满足条件时”的逻辑补回流程图、时序图和文字结论。
- 删除没有依据的“必然、全部、只能、不会”等绝对表述。

### 接口和状态是否对应当前实现

- 接口地址和请求方式是否与 Controller/Handler 一致。
- 状态机是否与状态枚举、状态校验和状态更新代码一致。
- 数据库关系图是否与 SQL、实体和 Mapper/Repository 的实际读写关系一致。

修复后重新检查图形、数据模型、核心流程和依赖的一致性。

## 7. 输出质量

- 文档严格遵循模块模板的 1～4 章。
- 删除通用常识、重复说明和与模块无关的测试清单。
- Mermaid 使用 `flowchart`、`sequenceDiagram`、`stateDiagram-v2` 和 `erDiagram`；其中触发业务场景和数据流向用 `flowchart`，主流程用 `sequenceDiagram`，状态机用 `stateDiagram-v2`，数据模型用 `erDiagram`。
- Mermaid 使用标准 Markdown 代码围栏，兼容飞书文档导入。
- 只有确实无法从代码、数据库或历史资料确认的内容才写“待确认”。
