# 模块系统文档整理

作者/负责人：CJ
邮箱：chenjia@fehorizon.com

## 目标

把一个系统模块整理成三部分内容：

1. **模块定位**：搞清楚这个模块是干嘛的——职责与边界、归属与上下游、核心价值、触发业务场景。
2. **接口与数据流**（最优先）：对外暴露什么、数据从哪里来到哪里去、核心数据模型和状态机。
3. **内部架构与核心流程**：分层结构、主流程时序图、分支流程（失败、重试、补偿、降级、兜底）、依赖。

最终文档只输出整理结果、接口和代码定位、状态变化、数据关系及必要的待确认项，不输出取证过程或论证过程。

## 文档结构

严格使用 [模块系统文档模板](references/scenario-template.md)：

1. 模块定位
2. 接口与数据流
3. 内部架构与核心流程
4. 参考文档

其中第 2 章最优先整理；状态流转是重灾区，必须逐条核对真实业务动作和触发条件。

## 内容要求

### 模块定位

- 职责：一句话说明这个模块解决什么业务问题；明确不做什么，边界很重要。
- 归属：属于哪个系统/子系统；上游是谁、下游是谁，分别交换什么。
- 核心价值：判断模块本质是计算、存储、消息转发、权限、数据同步，还是对外 API 网关。
- 业务场景：哪些业务流程会触发这个模块？区分正常流程和典型异常场景，每个场景写清本模块的动作和结果，可用简单 `flowchart` 表达触发来源到输出流向。

### 接口与数据流

- 对外暴露：完整列举 HTTP 接口、Dubbo、MQ 消息、定时任务、数据库触发器等入口，标注调用方或触发方式；核心入口展开写清入参、出参、错误码、限流、超时、重试策略，以及 Controller/Handler、Service、核心方法的代码定位。
- 数据流向：数据从哪里进来 → 模块内部处理 → 输出到哪里（DB、MQ、缓存、其他服务），用 Mermaid `flowchart` 表达。
- 核心数据模型：主要表/对象、关键字段、主键、外键、状态机。
  - 使用 Mermaid `erDiagram` 表达表关系，表框只保留表达关系所需的主键/外键或关联字段。
  - 每个业务对象单独绘制 `stateDiagram-v2` 状态机，每条状态迁移对应真实业务动作和触发条件；不把接口执行中间状态、按钮名称或数据库处理步骤当作业务状态。

### 内部架构与核心流程

- 整体结构：分层（controller/service/dao）、核心类、核心组件。
- 主流程：用最简 `sequenceDiagram` 时序图描述正常链路，包含真实参与方、调用方向、数据库操作和上下游依赖。
- 分支流程：失败、重试、补偿、降级、兜底逻辑逐条写清触发条件、处理方式和结果。
- 依赖：依赖哪些中间件（Redis、MySQL、RocketMQ、ES 等）、依赖其他服务哪些接口，写清用途和失败处理。

## 工具优先级

### 业务代码：优先 `codegraph`

1. 按模块名、业务对象、接口名、状态枚举和关键方法查询符号。
2. 沿调用链追踪 Controller/Handler、Service、领域方法、事务、消息、定时任务和外部客户端。
3. 对每个对外入口定位接口入口、核心方法、重要分支、状态更新、数据库写入和上下游调用。
4. 只有索引不存在、查询不到或信息不足时，才使用 `rg`、文件读取或其他代码搜索方式补充。

### 数据库：优先 `mysql-mcp-server`

1. 查询模块涉及的表、关键字段、主键、外键、唯一约束、状态字段和来源单据关联。
2. 只读确认实际读写关系、上下游单据关系、软删除和审计关系。
3. 状态流转必须对照状态字段、状态枚举和状态更新 SQL 确认。
4. 连接不可用、权限不足或目标不是 MySQL 时，再读取建表脚本、实体类、Mapper/Repository、迁移脚本或 ERD。

### 历史文档

读取 PRD、接口文档、业务规则、会议纪要、思维笔记和历史实现说明，用于补充业务术语、上下游角色和场景名称。当前代码和当前数据库模型优先于历史描述。

## 分析流程

### 1. 先定位模块

- 确定模块解决的业务问题和核心业务对象，一句话说清职责和不做什么。
- 判断核心价值类型：计算、存储、消息转发、权限、数据同步，还是对外 API 网关。
- 找出上游、下游，确认相互之间交换什么。
- 区分真实业务事件和系统内操作按钮。
- 列出触发模块的业务场景，区分正常流程和典型异常场景。

### 2. 再盘对外暴露（最优先）

- 从页面、HTTP、Dubbo、MQ、定时任务、数据库触发器完整列举入口，标注调用方或触发方式。
- 对核心入口扒到 Controller/Handler、Service、核心方法、重要条件分支。
- 记录入参、出参、错误码、限流、超时、重试策略。

### 3. 梳理数据流向和数据模型

- 画清数据从哪里进来、内部怎么处理、输出到哪里（DB、MQ、缓存、其他服务）。
- 用 mysql-mcp-server 确认主要表、关键字段、主键、外键和状态字段。
- 每个业务对象单独绘制状态机，每条状态迁移对应真实业务动作和触发条件。

### 4. 还原主流程

- 确认分层结构、核心类和核心组件。
- 画最简时序图描述正常链路：入口 → 校验 → 核心处理 → 数据写入 → 上下游联动 → 返回。

### 5. 补全分支流程和依赖

- 逐条确认失败、重试、补偿、降级、兜底的触发条件、处理方式和结果。
- 确认中间件依赖和其他服务接口依赖，写清用途和失败处理。

### 6. 评估文档准确性并修复

文档生成后，必须进行一次独立的准确性评估，不能直接把初稿交付。先从文档中定位高风险断言，再逐条对照功能代码和数据关系；发现问题时直接修正文档，并重新执行本步骤。

高风险断言优先包括：

- “一定会”“必然生成”“所有场景都”“只能”“不会重复”等绝对表述。
- 接口地址、请求方式、Controller/Handler、Service、核心方法。
- 业务状态、状态迁移、入参出参和错误码。
- 上游/下游调用、消息、回写、联动、事务、重试、超时和补偿。
- 数据表之间的生成、关联、更新、作废和回写关系。
- 业务场景的触发条件、本模块动作和结果。

按以下三层检查：

1. **事实支撑层**：每个高风险断言是否能在当前业务代码或数据库关系中找到直接支撑；找不到就改为“待确认”，或删除。
2. **条件分支层**：检查文档是否把带条件的逻辑写成必然结果；将权限、状态、配置、组织/账套、数据是否存在、外部调用结果等条件补回流程和结论。
3. **实现对应层**：逐条核对接口与当前实现、状态与状态更新代码、表关系与实际 SQL/实体/Mapper 操作是否一致；不一致时以当前实现为准并修正文档。

修复后再次检查：

- 流程图、时序图、状态图和数据模型没有互相矛盾。
- 对外暴露清单没有遗漏页面、接口、消息、定时任务等主要入口。
- 数据库关系图没有画出当前实现不存在的关系。
- 文档中的“必然、全部、只能、不会”等绝对表述都有明确实现依据。

### 7. 提醒并确认导入飞书云盘

这是文档交付前的最后一步，默认只提醒，不自动执行导入。

1. 生成并修复 Markdown 文档后，提醒用户录入目标飞书云盘目录位置。
2. 在用户没有提供目录位置前，不执行任何上传或导入。
3. 用户提供目录位置后，再明确询问是否确认导入；未明确确认时，不执行导入。
4. 用户确认后，导入 Markdown 文档到指定飞书云盘目录。
5. 导入时逐段识别文档中的 Mermaid 代码块，将所有 Mermaid 内容放入飞书文档的“放大文本绘图组件”中，不能只把 Mermaid 源码作为普通文本保留。
6. 导入完成后检查文档章节、图片/绘图组件、流程图、时序图、状态图和数据库关系图是否齐全，并反馈导入结果。

导入时遵循飞书相关技能的权限和资源操作规则；没有得到用户的目录位置和明确确认，不得调用上传、创建或移动文档的操作。

## 输出要求

- 中文 UTF-8 Markdown，兼容飞书文档导入。
- 所有图形优先使用标准 Mermaid：
  - 触发业务场景、数据流向用 `flowchart`
  - 主流程用 `sequenceDiagram`（最简时序图）
  - 状态机用 `stateDiagram-v2`
  - 数据模型用 `erDiagram`
- Mermaid 必须使用 ` ```mermaid ` 代码围栏。
- 不使用 HTML、内嵌 SVG、图片 data URI、合并单元格或自定义渲染语法。
- 对外暴露用清单表格呈现，保留类型、入口、调用方/触发方式列。
- 删除通用常识、重复内容、泛化测试清单和不准确的核心字段罗列。
- 无法确认的内容只写简短的“待确认：具体问题”，不展开论证。
- 文档生成完成后必须提醒用户确认飞书云盘目录；确认前不得导入。

## 自检

- 模块定位是否说清职责、不做什么、归属、上下游和核心价值。
- 触发业务场景是否区分正常流程和典型异常场景。
- 对外暴露是否覆盖 HTTP、Dubbo、MQ、定时任务、触发器等主要入口；核心入口是否有入参、出参、错误码、限流、超时、重试和代码定位。
- 数据流向是否写到 DB、MQ、缓存、其他服务的输出终点。
- 状态机是否逐条对应真实业务动作，是否遗漏独立状态机。
- 主流程时序图是否最简且覆盖正常链路。
- 分支流程是否覆盖失败、重试、补偿、降级、兜底。
- 依赖是否写清中间件和其他服务接口及失败处理。
- 数据库关系图是否只包含真实相关表，并能看出表关系。
